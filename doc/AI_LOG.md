# AI_LOG — SETOUT 개발 기록

이 문서는 SETOUT을 만들면서 AI를 어떻게 사용했는지에 대한 일지다.
단계마다 그때의 설계 판단, AI에 준 지시, 검증 결과를 남긴다.

기록의 초점은 "AI가 무엇을 만들어 주었는가"가 아니라
**무엇을 제약했고, 무엇을 기각했으며, 어떻게 검증했는가**에 둔다.
결과물의 책임은 전부 사람에게 있고, AI는 그 판단을 빠르게 시험해 보는 도구다.

## 외부 에셋 / 오픈소스

**없음.** 이미지·사운드·폰트·라이브러리를 일절 쓰지 않는다.
게임 전체가 순수 HTML + JavaScript + Canvas 2D이며,
화면에 보이는 모든 것은 좌표 계산으로 그린다.
3D 엔진도 물리 엔진도 쓰지 않는다.

범용 엔진의 카메라와 깊이 버퍼는 오히려 그 정확도를 방해한다.
직접 좌표를 계산하는 쪽이 이 게임에서는 더 정확하다.

## 검증

작업 내내 지킨 원칙이 하나 있다. **눈으로 보고 "되는 것 같다"로 넘어가지 않는다.**
좌표 변환은 틀려도 화면상 그럴듯해 보이고, 깊이 정렬은 겹치기 전까지 증상이
없으며, 잉크 회계는 한참 플레이해 봐야 어긋난 것이 드러난다.
이런 것들은 전부 코드로 확인했고, 그 스크립트를 저장소에 함께 둔다.

```
node test/run.mjs
```

외부 테스트 프레임워크를 쓰지 않는다. 게임이 라이브러리를 하나도 쓰지 않는데
검증만 의존성을 들이면 "설치 없이 실행"이라는 전제가 흐려진다.
각 묶음은 통과 여부를 종료 코드로 돌려주고 `run.mjs` 가 그것을 모은다.

## AI에 준 상시 지시 (디렉팅 원칙)

작업 내내 유지한 지시다. 매 작업마다 반복해서 요구했다.

1. **코드를 쓰기 전에 구조와 원리를 먼저 설명할 것.**
   설명이 납득되지 않으면 코드는 보지 않는다.
   구현을 받는 것보다 설계를 검증하는 것이 먼저다.

2. **결정이 필요한 지점에서는 임의로 고르지 말고 선택지와 근거를 제시할 것.**
   특히 되돌리기 비싼 결정(좌표계, 그리기 평면, 데이터 구조)은
   반드시 사람이 고른다.

3. **눈으로 보고 "되는 것 같다"로 넘어가지 말 것.**
   좌표 변환처럼 틀려도 그럴듯해 보이는 코드는
   반드시 자동 검증 스크립트로 확인한 뒤에 진행한다.

4. **단계마다 커밋하고, 커밋 전에 확인받을 것.**
   커밋 메시지에는 무엇을 했는지가 아니라 **왜 그렇게 했는지**를 쓴다.

## 1단계 — 좌표계와 그리기

### 완성한 것

- 등각 투영 좌표계 (`src/iso.js`)
- 청사진 바닥 격자 렌더 (`src/render.js`)
- 화면 크기에 맞춰 판 전체를 담는 자동 축척 카메라
- 커서 위치 → 격자 칸 역변환 + 하이라이트 (`src/input.js`)
- 드래그로 획을 긋고, 손을 떼면 철판으로 확정 (`src/board.js`)
- 우클릭 드래그로 칸 단위 지우기
- GitHub Pages 배포 경로 확보

### 설계 판단

#### 1. 착시의 근거를 상수 하나에 묶었다

등각 투영식은 다음과 같다.

```
sx = OX + (x - y) * TILE_W/2
sy = OY + (x + y) * TILE_H/2 - z * BLOCK_H
```

여기서 `BLOCK_H`를 `TILE_H`와 같은 값으로 두면
`(x+1, y+1)` 이동과 `(z-1)` 이동이 화면상 **완전히 같은 픽셀 이동**이 된다.
깊이 정보가 수학적으로 소멸하는 이 지점에서 착시가 발생한다.

이 등식이 게임의 전제이므로, 두 값을 각각 `32`로 쓰지 않고
`BLOCK_H = TILE_H`로 참조하게 두었다.
나중에 타일 크기를 조정하다 둘이 어긋나면 착시가 조용히 죽는데,
그런 사고는 테스트로 잡기 어렵고 증상도 모호하다.
구조적으로 불가능하게 만드는 편이 낫다.

#### 2. 그리기 평면을 z=0으로 못 박았다

착시 게임에서는 화면의 한 점이 여러 `(x, y, z)`에 대응한다.
그게 이 게임의 컨셉이지만, 동시에 **역변환이 불가능하다는 뜻**이기도 하다.
마우스가 가리키는 칸을 특정할 수 없으면 그리기 자체가 성립하지 않는다.

선택지는 세 가지였다.

- 커서가 닿은 표면에 그린다 → 후보 타일 레이캐스팅이 필요하고,
  겹친 후보 중 무엇을 고를지가 모호하다
- 작업 층을 플레이어가 직접 올리고 내린다 → UI가 늘고,
  "튜토리얼 문구 없음" 원칙과 충돌한다
- **바닥에만 그린다** → 채택

`z = 0`으로 고정하면 투영식을 뒤집는 것만으로 해가 하나로 확정된다.

```
u = (sx - OX) / (TILE_W/2)   →  u = x - y
v = (sy - OY) / (TILE_H/2)   →  v = x + y
x = (u + v) / 2,  y = (v - u) / 2
```

높이는 그리기에서 분리해, **그린 뒤 판을 집어 올리는** 별도 동작으로 다룬다.
결과적으로 "그린다 → 집어서 높이를 조절한다 → 세운다"라는
기획 단계의 조작 흐름과도 정확히 맞아떨어졌다.

되돌리기 가장 비싼 결정이었으므로, 코드를 쓰기 전에 근거를 정리해 결정했다.

#### 3. 판이 한 덩어리인 것과, 그 위를 걸을 수 있는 것을 분리했다

획을 확정할 때 서로 붙은 칸들을 하나의 판으로 묶는데,
"붙었다"의 기준을 대각 포함(8방향)으로 잡았다.
대각선으로 그은 획이 칸 하나짜리 판으로 우수수 쪼개지면
"한 번 그었으니 한 장의 철판"이라는 직관이 깨진다.

반면 **이동은 사방 인접만 인정한다.**
이동 판정은 화면상 인접(±TILE_W/2, ±TILE_H/2)으로 하는데
그것이 사방 인접에 해당하기 때문이다.

즉 대각선 판은 한 장으로 집어 옮길 수 있지만 그 위를 대각으로 건널 수는 없다.
같아 보이는 두 개념을 일부러 다른 규칙으로 둔 것이며,
성의 없이 사선을 긋는 것과 길을 제대로 잇는 것이 구분되므로
게임에도 이롭다고 판단했다.

#### 4. 화면 크기에 관계없이 판 전체가 보이게 했다

24×24 격자의 화면상 가로 폭은 1536px이라
개발 중인 창에서 이미 좌우가 잘렸다. 노트북 해상도에서는 더 심해진다.
심사자가 링크를 열었을 때 첫 화면이 잘려 있으면 그것으로 끝이므로,
격자 수를 줄이는 대신 창에 맞춰 균등 배율을 잡는 카메라를 넣었다.

여기서 확인이 필요했던 것은 **배율이 착시를 깨지 않는가**였다.
균등 배율은 착시 등식의 양변에 똑같이 곱해지므로 등식을 보존한다.
가로·세로를 따로 늘리는 비균등 배율만 등식을 깬다.
수식으로 확인한 뒤 실제 코드에서도 검증했다(아래 참조).

부수 효과로, 판 크기가 층마다 달라져도 화면이 알아서 맞는다.
AI 레벨 디렉터가 층마다 판 크기를 자유롭게 정할 수 있게 됐다.

#### 5. 획이 부지 밖으로 나가도 취소하지 않는다

드래그 도중 커서가 부지 밖으로 나가는 일은 흔하다.
그때 획 전체를 버리면 공들여 설계한 모양이 손목 실수로 날아간다.
그래서 밖으로 나간 구간은 무시하고, 다시 들어오면 이어서 그린다.

다만 밖을 지나온 구간은 잇지 않는다.
그 결과 획이 두 덩어리로 갈라질 수 있는데, 확정할 때 연결 성분으로 쪼개
각각 독립된 판으로 만든다.
멀리 떨어진 조각이 한 판으로 묶이면
판 하나를 집어 올렸을 때 화면 반대편 조각이 같이 떠오르기 때문이다.

#### 6. 빠른 드래그로 생기는 구멍을 메운다

`pointermove`는 프레임 단위로 오므로, 빠르게 그으면
`(3,3)` 다음에 `(7,5)`가 찍히고 사이 칸이 통째로 빈다.
구멍 뚫린 획은 잉크 계산과 길 연결을 동시에 어긋나게 하므로
두 칸 사이를 격자 직선(Bresenham)으로 메운다.

#### 7. 지우기는 새로 짤 로직이 거의 없었다

판 일부를 지우면 남은 것이 갈라질 수 있다. ㄷ자 판의 가운데를 지우면
남는 것은 판 둘이고, 쪼개 두지 않으면 한쪽을 집어 올릴 때 떨어진 다른 쪽이
같이 떠오른다.

그런데 이 판정은 **획을 확정할 때 쓰던 연결 성분 분해와 같은 함수**다.
지우기는 "판에서 칸을 빼고 남은 것을 다시 덩어리로 나누는" 일이기 때문이다.
설계를 잘해서라기보다, 획을 확정할 때 이미 같은 문제를 풀어 두었기 때문에
그 함수가 그대로 맞아떨어졌다.

그리기와 달리 지우기는 즉시 반영한다. 획은 전체가 모여야 판 하나가 되므로
손을 뗄 때까지 확정을 미뤄야 하지만, 지우기는 칸 하나하나가 독립적이라
미룰 이유가 없고 지우개는 문지르는 즉시 지워져야 지우개답다.
덩어리 재분해만 손을 뗄 때 한 번 한다. 지우기는 칸을 빼기만 하므로
한 번 갈라진 판이 도로 붙는 일이 없다.

### AI 디렉터의 실행 형태를 정했다

출품의 핵심이자 가장 위험한 결정이라 가장 먼저 확정했다.

GitHub Pages는 정적 호스팅이므로 API 키를 둘 수 없고,
심사자에게 키 입력을 요구하는 것은
"링크 클릭만으로 브라우저에서 바로 플레이"라는 제출 조건에 어긋난다.
런타임에 외부 모델을 호출하는 구성은 이 시점에서 배제됐다.

채택한 구조는 두 층이다.

- **게임 안**: 생성 → 솔버 검증 → 실패 이유 판정 → 재설계 루프를
  클라이언트 코드로 구현한다. 검증기는 이동 판정에 쓰는 BFS를 그대로 재사용한다.
  같은 코드를 두 번 쓰지 않는 구조로 잡았다.
- **개발 단계**: 그 루프의 설계, 평가 기준, 실패 시 되돌릴 조건을
  Claude와 함께 만들고 그 과정을 이 문서에 남긴다.

즉 **AI는 런타임의 부품이 아니라 설계 단계의 상대**이고,
런타임에서 도는 것은 그 설계의 결과물이다.
이 구분을 흐리지 않는 것이 이 문서의 목적이기도 하다.

### 검증

좌표 변환은 틀려도 화면상 그럴듯해 보이기 때문에 눈으로 확인하지 않았다.
Node로 검증 스크립트를 돌려 다음을 확인했다.

**좌표계** (5가지 창 크기: 1489×863 / 1366×768 / 1920×1080 / 3840×2160 / 900×600)

| 항목 | 결과 |

세 번째 항목이 착시의 성립 조건이다.

| 대각선 획이 판 한 장으로 묶이는가 | 통과 |
| 이미 판이 깔린 칸을 건너뛰고 그 자리에서 획이 갈라지는가 | 통과 |
| 부지 밖 좌표를 칠하지 않는가 | 통과 |
| 획 취소가 확정된 판을 건드리지 않는가 | 통과 |

### AI에 준 주요 지시

원문 그대로가 아니라 요지로 옮긴다.

- *"기획 정리 파일을 자세히 읽고, 단계별로 논의하면서 진행할 것."*
  → 전체 구현을 한 번에 받지 않고 단계를 쪼갠 이유.
  한 번에 받은 코드는 검증할 수 없고, 문제가 생겼을 때 어디가 원인인지도 알 수 없다.

- *"코드를 쓰기 전에 구조와 원리를 먼저 설명할 것."*
  → 그리기 평면을 z=0으로 고정한 결정이 여기서 나왔다.
  설명을 요구하지 않았다면 "커서가 닿은 표면에 그린다"로 구현이 시작됐을 것이고,
  레이캐스팅과 모호한 후보 선택 문제를 뒤늦게 만났을 것이다.

- *"양쪽 끝이 잘려 있으니 확인해 달라."*
  → 격자 수를 줄이는 즉효 대신 원인(1536px 대 창 폭)을 먼저 규명하게 했고,
  그 결과 자동 축척 카메라라는 구조적 해결로 갔다.
  동시에 "배율이 착시를 깨지 않는가"라는 검증 항목이 새로 생겼다.

- *"눈으로 확인하지 말고 검증 스크립트로 확인할 것."*
  → 위 검증 표가 여기서 나왔다.

- *"기획·전략 메모는 저장소에 올리지 말 것."*
  → 공개 저장소에 들어갈 것과 개인 메모를 분리했다.

## 2단계 — 잉크 경제

### 완성한 것

- 잉크 소모와 절반 환급 (`src/config.js`, `src/board.js`)
- 획을 긋는 중 실시간 소모 미리보기
- 잉크 게이지 (`src/render.js`)
- 판이 바닥 격자를 넘어가던 렌더 오류 수정
- 바닥 크기 조정 (24×24 → 16×16)

### 설계 판단

#### 1. 지우면 절반만 돌아온다

전액 환급으로 두면 잉크는 "총량 제약"이 아니라 "한 번에 깔 수 있는 양"으로
축소된다. 그리는 총량이 무제한이 되면 다리를 그리는 값이 사실상 0 이 되어
착시를 쓸 이유가 사라진다. 반대로 환급이 아예 없으면 실수 한 번이
스테이지를 막아 가혹하다.

절반으로 두되, **소모 2 / 환급 1** 로 잡아 전부 정수로 떨어지게 했다.
소모 1 / 환급 0.5 로 두면 반올림 방향에 따라 한 칸을 그렸다 지우는 것만으로
잉크가 늘어나는 구멍이 생긴다. 부동소수점을 아예 들이지 않는 편이 안전하다.

환급률은 상수로 뺐다. 지우기를 남발하는 플레이어에게 환급을 줄이는 대응이
숫자 하나로 되므로, AI 디렉터가 쥘 두 번째 손잡이가 된다.

#### 2. 잉크는 확정된 것만 깎는다

긋는 중인 획은 잉크를 건드리지 않고, "지금 쓸 수 있는 잉크"를 계산할 때만
빠진다.

```
inkAvailable() = board.ink - stroke.size * INK_COST
```

한 줄이지만 세 가지가 따라온다. 실시간 미리보기가 별도 코드 없이 되고,
Esc 취소는 되돌릴 것이 없으며(깎은 적이 없으므로), 게이지는 확정 잉크와
이번 획이 먹을 몫을 진하기로 나눠 그릴 수 있다.

#### 3. 잉크가 다하면 그 지점에서 획이 멈춘다

획 전체를 거부하는 방식도 검토했으나, 왜 안 그어지는지 보이지 않아 답답하다.
긋다가 선이 안 나오는 것은 펜에서 잉크가 떨어지는 현상 그대로라
설명 없이 이해된다. 게이지를 보고 있지 않아도 즉시 알아챈다.

#### 4. 게이지에 숫자를 쓰지 않았다

대사도 문구도 없는 게임이므로 남은 양은 길이로만 읽힌다.
위치는 좌측 하단이고, 여백은 카메라가 판을 화면에 맞출 때 쓰는 값을
그대로 재사용했다. 판을 담고 남은 자리 안쪽이라 겹칠 일이 구조적으로 없다.

#### 5. 판이 바닥에 파묻혀 있었다

윗면을 바닥 평면에 놓고 두께를 아래로 뻗고 있었다. 등각 화면에서 아래쪽은
카메라에 가까운 방향이라, 그 두께가 앞칸의 바닥을 덮어 격자선을 넘어갔다.

두께를 위로 세워 격자와 맞는 것이 판의 **아랫면**이 되게 고쳤다.
바닥에 놓인 철판은 바닥 위에 얹혀야지 파묻히면 안 된다.

여기서 확인이 필요했던 것은 착시 등식이 깨지지 않는가였다.
모든 판이 똑같이 두께만큼 올라가므로 판끼리의 상대 정렬은 불변이고,
착시는 판과 판 사이의 관계에서 나오므로 영향이 없다. 코드로 확인했다.

#### 6. 배급이 인색해 보인 원인은 분자가 아니라 분모였다

24×24 바닥은 576칸이라 배급량 60칸이 10% 밖에 되지 않았다.
광활한 빈 바닥에 잉크 몇 방울처럼 보였다.

여기서 잉크를 늘리는 것이 직관적인 대응이지만, 그러면 제약 자체가 사라져
착시를 쓸 이유가 없어진다. 바닥을 16×16(256칸)으로 줄여 60칸이 약 23%를
차지하게 했다. 부수 효과로 일반 해상도에서 카메라 축소가 걸리지 않게 되어
격자선과 판이 원래 픽셀 크기로 나온다.

배급량은 판 크기에 연동시키지 않고 절대값으로 뒀다.
배급은 판 크기가 아니라 목표까지의 거리에 달려 있다.
비례식으로 묶으면 나중에 디렉터가 둘을 독립적으로 조절할 수 없다.

### 검증이 설계 판단을 반증했다

**이 항목이 이 단계의 핵심이다.**

절반 환급을 고르면서 "이러면 징검다리 이동이 막힌다"고 판단했다.
앞에 그리고 뒤를 지우며 전진하는 전략인데, 전액 환급이면 잉크 소모 없이
무한히 전진할 수 있으므로 절반 환급이 이를 차단한다고 본 것이다.

검증 스크립트가 이를 반증했다.

```
직접 그리기   60칸
징검다리     110칸   ← 1.8배 유리
```

칸당 실질 비용이 `INK_COST - INK_REFUND` 로 떨어지기 때문이다.
**환급이 0보다 크면 징검다리는 언제나 길게 그리는 것보다 싸다.**
환급률로 조절할 수 있는 문제가 아니었고, 판단이 틀렸다.

그대로 뒀다면 최적 전략이 "앞에 그리고 뒤를 지우는 지루한 반복 조작"이 되고,
AI 디렉터가 읽어야 할 잉크 사용량 지표도 흐려졌을 것이다.
플레이해 보고 나서야 발견했을 종류의 문제이고, 그때는 잉크 설계 전체를
다시 손봐야 했을 것이다.

막는 방법은 환급률이 아니라 환급 조건이다.
**"캐릭터가 밟은 판은 환급하지 않는다."** 밟지 않은 판은 그대로 환급되므로
설계 실험은 공짜로 남고 회수만 비싸진다. 캐릭터가 4단계에 오므로 지금은
구현할 수 없어 그 단계의 필수 항목으로 올려 두고, 구멍의 존재와 실측값을
계획 문서에 명시했다.

이것이 "눈으로 확인하지 말고 검증 스크립트로 확인할 것"이라는 지시가
실제로 일한 사례다. 검증의 목적은 코드가 의도대로 도는지 확인하는 것이지만,
때로는 **의도 자체가 틀렸다는 것**을 알려준다.

### AI에 준 주요 지시

- *"지우면 잉크 절반만 돌아오게 하는 게 좋을 것 같은데, 다른 아이디어 있어?"*
  → 결론은 처음 안을 유지하는 것이었지만, 대안 셋을 검토하는 과정에서
  "밟은 판은 환급 없음"이라는 안이 나왔고 그것이 나중에 징검다리 구멍의
  해법이 됐다. 채택하지 않은 선택지가 나중에 쓰인 경우다.

- *"판이 바닥선을 넘어가는 것 같다."*
  → 증상만 전달하고 원인을 지정하지 않았다. 두께를 줄이는 즉효 대신
  좌표계 수준에서 원인을 규명하게 했고, 그 결과 렌더 방식 자체를 고쳤다.

- *"판을 그릴 수 있는 개수가 너무 적은 것 같다. 바닥 칸의 2/3 정도는
  그릴 수 있어야 하지 않나?"*
  → 요청대로 잉크를 6배 늘리면 제약이 사라져 착시를 쓸 이유가 없어진다는
  점을 먼저 확인받았고, 원인이 분자가 아니라 분모라는 분석 끝에
  바닥을 줄이는 쪽으로 갔다. 요청을 그대로 실행하지 않고 목적을 되짚은 경우다.

- *"커밋을 4개로 나눠 달라."*
  → 한 번에 작업한 내용을 성격별로 갈랐다. 나누는 과정에서 각 커밋 시점의
  파일 상태를 복원했으므로, 어느 커밋으로 되돌려도 동작한다.

## 3단계 — 판 높이

### 완성한 것

- 판 높이 `z` 와 상·하한 (`src/config.js`)
- 화면 좌표로 판을 집는 `pickAt` (`src/board.js`)
- 휠로 판 높이 올리고 내리기 (`src/input.js`)
- 지우기와 하이라이트를 집기 함수로 통일 — 뜬 판도 지워진다
- 카메라 여유를 높이 상한에서 파생 (`src/iso.js`)
- 검증 스크립트를 저장소로 옮기고 한 줄로 돌게 정리 (`test/`)

### 설계 판단

#### 1. z 는 화면에서 수직으로만 움직인다

코드를 쓰기 전에 투영식부터 풀었다. 두 투영이 같은 픽셀에 오는 조건을
정리하면 이렇게 된다.

```
sx 일치:  x − y = x′ − y′
sy 일치:  (x + y) − 2z = x′ + y′        (BLOCK_H = TILE_H 이므로)
─────────────────────────────────────
          x′ = x − z ,  y′ = y − z
```

**`(x, y, z)` 는 바닥의 `(x−z, y−z)` 자리에 나타난다.** 이 한 줄에서 3단계가
전부 파생됐다.

첫째, z 는 `sx` 를 조금도 바꾸지 않는다. 판을 아무리 올려도 화면 가로 위치는
고정이다. 따라서 착시로 이을 수 있는 판은 애초에 **화면상 같은 세로줄에 있는
것뿐**이고, 높이 조절은 그 줄 안에서 위아래를 맞추는 일이다.
5단계에서 착시 후보를 찾을 때 탐색 공간이 이미 이만큼 좁혀져 있다.

둘째, 역변환이 다시 성립한다. 1단계에서 그리기를 `z=0` 으로 못 박은 이유가
"화면 한 점 → 무한히 많은 `(x,y,z)`" 였는데, 판의 z 에 상한이 있으면 후보가
`(gx+z, gy+z, z)` 로 유한해져 **열거할 수 있다.**

#### 2. 집기 함수 하나가 네 곳에 쓰인다

계획서의 3단계 체크리스트는 네 줄이었지만, 실제로는 `z=0` 시절의 가정 위에
서 있던 코드 세 곳이 조용히 깨졌다.

| 깨지는 곳 | 왜 |
|---|---|
| 지우기 | 커서가 준 바닥칸으로 판을 조회했다 — 뜬 판은 안 지워진다 |
| 하이라이트 | 언제나 `z=0` 에 그렸다 — 뜬 판 위에서 엉뚱한 칸이 빛난다 |
| 카메라 여유 | 높이 상한과 무관한 독립 상수였다 — 상한을 올리면 판 머리가 잘린다 |

그래서 이 단계의 실제 구조는 **함수 하나를 만들고 여럿이 그것을 쓰는 것**이
됐다. `pickAt(gx, gy)` 은 그 자리에 올 수 있는 후보를 위에서부터 훑어 처음
걸리는 것을 돌려준다. 위에서부터 훑는 것이 맞는 이유는 후보들의 정렬 키를
펴 보면 나온다.

```
depthKey = x + y + z = (gx+z) + (gy+z) + z = gx + gy + 3z
```

z 에 대해 단조증가하므로 z 가 큰 후보가 언제나 위에 그려진다.
렌더가 쓰는 정렬과 같은 식이라 둘이 어긋날 수 없다.

휠·지우기·하이라이트·그리기 차단이 전부 이 함수를 쓰고,
5단계의 "겹친 후보 중 실제로 보이는 것" 도 같은 함수다.
1단계에서 연결 성분 분해 하나가 획 확정과 지우기 양쪽에 맞아떨어졌던 것과
같은 모양이다.

#### 3. 깊이 정렬은 z 가 붙어도 동률이 나지 않는다

`z` 가 전부 0인 동안에는 화면상 겹침이 아예 없었으므로,
`depthKey = x + y + z` 정렬은 지금까지 한 번도 시험받은 적이 없었다.
겹침이 여기서 처음 발생한다.

정렬 키를 화면 좌표로 펴면 `key = x′ + y′ + 3z` 다. 두 칸의 그림이 겹치려면
바닥 투영이 최대 한 칸 차이여야 하므로 `D = (x′+y′)_A − (x′+y′)_B` 는
`0, ±1, ±2` 중 하나다. 동률이 되려면 `D = −3Δz` 여야 하는데 `±1, ±2` 에는
정수해가 없고, `D = 0` 은 같은 칸일 때뿐이다.

**겹치는 두 칸의 정렬 키는 절대 같아지지 않는다.** 순서가 임의로 정해지는
구간이 원천적으로 없다. 손으로 푼 것이므로 전수 스크립트로 다시 확인했다.

#### 4. 높이 상한 8, 하한 0

상한이 없으면 같은 세로줄 위의 어떤 판이든 높이만 맞추면 이어지므로 퍼즐이
헐거워진다. 반대로 너무 조이면 이을 수 있는 조합이 드물어 착시가 좀처럼
성립하지 않는다. 8 은 바닥의 절반이고, 대각으로 8칸 떨어진 판까지 이을 수
있다는 뜻이다.

상한을 올리면 카메라가 그만큼 위를 비워야 해서 화면이 작아진다.
설계값이 화면 크기와 직접 묶여 있다는 것을 상한을 정할 때 같이 확인했다.

하한은 0 이다. 음수 z 는 판을 격자선 아래로 내려보내, 2단계에서 두께를 위로
세워 고쳤던 "바닥에 파묻힘" 을 그대로 되살린다.

높이 조절에는 잉크를 쓰지 않는다. "그리는 것은 비싸고 착시는 공짜" 가 이
게임의 뿌리인데 높이는 착시를 만드는 바로 그 수단이다. 여기에 값을 매기면
2단계 설계 전체가 무너진다. 대신 **상한 자체가 AI 디렉터의 세 번째 손잡이**가
된다(잉크 배급량, 환급률에 이어). 층마다 상한을 조이면 착시 가능 조합이
직접 줄어든다.

#### 5. 판을 올려도 기둥은 놓지 않는다

되돌리기 비싼 결정이라 선택지를 정리해 사람이 골랐다.

판을 위로 띄우면 그 아래 바닥칸이 비는가? 비워 주면 뜬 판 밑으로 다른 다리를
통과시키는 입체 교차로를 만들 수 있어 표현력이 넓다. 대신 한 `(x,y)` 에 판이
여럿 겹칠 수 있게 되어 `(x,y) → 판` 조회가 1:1 이 아니게 된다.
지우기·잉크 회계·연결 성분 분해가 전부 그 조회 위에 서 있으므로 셋 다 다시
짜야 한다. 그리고 착시는 화면상 정렬로 성립하지 층 쌓기로 성립하지 않으므로
얻는 것도 없다.

**기둥을 계속 잡아 두는 쪽으로 정했다.** 2층 구조를 못 만드는 것이 대가다.

#### 6. 휠은 잡은 판을 놓지 않는다

판을 한 칸 올리면 그 판은 화면에서 `(x−z, y−z)` 만큼, 즉 위쪽 뒤로 빠진다.
커서는 그대로 있으므로 **매번 다시 집으면 한 칸 올리고 놓치기를 반복한다.**
제스처가 시작될 때 잡힌 판을 붙잡아 두고, 커서가 움직일 때 놓는다.
휠을 굴리는 동안 커서는 보통 가만히 있으므로 제스처 전체가 한 판에 걸린다.

하이라이트도 잡은 판을 따라 올라간다. 무엇을 쥐고 있는지 보여야 한다.

#### 7. 휠 값은 크기를 재지 않고 종류를 가른다

`deltaY` 는 장치마다 값이 딴판이다. 휠 마우스는 한 번에 100 안팎을 보내고,
트랙패드는 4 정도를 잘게 여러 번 보내며, 단위 자체가 픽셀·줄·페이지로 갈린다.
어느 한쪽에 문턱을 맞추면 다른 쪽이 죽거나 폭주한다.

그래서 크기를 재는 대신 종류를 갈랐다. 한 번에 크게 오면 그것이 노치 하나이고
값의 크기는 무시한다. 잘게 오면 쌓아서 문턱을 넘을 때 한 칸.

### 검증

**좌표계와 정렬** (32항목, 전부 통과)

| 항목 | 결과 |
|---|---|
| 2,304칸(256×9) 윗면을 찍어 그 칸이 다시 잡히는가 — 5가지 창 크기 | 통과 |
| 겹치는 칸 쌍 67,800개에 정렬 동률이 없는가 | 통과 |
| **집기 결과 = 렌더 결과** (배치 30개, 표본 3,375점) | 통과 |

| 착시 등식 `(4,4,z=2) = (3,3,z=1)` — 1단계 검사 재실행 | 통과 |
| z 가 `sx` 를 바꾸지 않는가 | 통과 |
| 뜬 판을 집고 지울 수 있는가 / 한 기둥에 판은 하나뿐인가 | 통과 |

세 번째가 이 단계의 핵심이다. 앞의 두 항목은 손으로 푼 계산을 자기 자신으로
검산하는 것에 가깝지만, 이것은 **집기와 렌더라는 독립된 두 경로가 같은 답을
내는지**를 본다. 검증 쪽은 `screenToGrid` 를 쓰지 않고 화면 다각형 포함
판정으로 "실제로 덮는 칸" 을 따로 구해 비교하므로 두 경로가 논리를 공유하지
않는다. 여기가 어긋나면 5단계에서 "이어져 보이는데 못 건너간다" 로 나타난다.

이 단계에서 검증 스크립트를 저장소로 옮겼다. 지금까지는 개발 환경에만 두고
결과 표만 이 문서에 옮겼는데, 그러면 **확인할 수 없는 주장**이 된다.
`node test/run.mjs` 한 줄로 전부 돈다.

### 죽은 상태가 설계 오류를 드러냈다

그리기 차단을 처음에는 화면 기준으로만 바꿨다. "눈에 보이는 판에 가려진
자리에는 그리지 않는다" 는 규칙 자체는 옳고, 판 위에 덧그려지는 것도 막힌다.

구현을 끝내고 `occupied` 집합이 어디에 쓰이는지 훑다가, **쓰기만 하고 읽지
않는 상태가 되어 있는 것**을 발견했다. 같은 사실을 두 군데에 적어 두고 한쪽만
보고 있으면 둘이 어긋나도 아무도 모른다.

지워도 되는지 따져 보다 실제 문제를 찾았다. 판을 올리면 그 판은 화면에서
원래 자리를 떠나므로, 화면 기준으로만 막으면 **비어 보이는 그 기둥에 두 번째
판을 그릴 수 있다.** 한 `(x,y)` 에 판이 둘 생기는 순간 지우기가 어느 쪽을
가리키는지 알 수 없어진다. 방금 사람이 고른 규칙이 막으려던 상황이 정확히
이것이었는데, 구현이 조용히 다른 규칙으로 바뀌어 있었다.

기둥 검사와 화면 검사를 둘 다 걸었다. 앞의 것이 조회의 유일성을 보장하고,
뒤의 것이 안 보이는 자리에 잉크가 새는 것을 막는다. 그리고 이 성질을 지키는
검사를 검증 스크립트에 추가했다.

2단계에서 검증 스크립트가 설계 판단을 반증했다면, 여기서는 **읽히지 않는
상태가 구현이 설계에서 벗어난 것을 드러냈다.** 규칙을 정하는 것과 코드가 그
규칙대로 도는 것은 별개이고, 후자는 따로 확인해야 한다.

### 브라우저에서만 안 되는 것

구현을 마치고 휠이 안 된다는 보고를 받았다. 코드를 고치기 전에 먼저
재현했다. 가짜 캔버스에 실제 `attachPointer` 를 물리고 휠 이벤트를 직접 쏘는
스크립트를 만들었더니 판이 정상적으로 오르내렸다.

로직이 정상이면 남는 것은 브라우저 쪽이다. 원인은 **구버전 모듈 캐시**였다.
`input.js` 의 옛 판본에는 휠 리스너가 아예 없으므로 그리기·지우기는 멀쩡한데
휠만 죽은 증상과 정확히 맞는다. 개발 서버가 `Cache-Control` 을 보내지 않아
브라우저가 알아서 캐시하고 있었다.

브라우저마다 결과가 달랐을 때도 추측하지 않고, 원인을 가르는 진단 페이지를
만들어 확인했다. 모듈에 휠 리스너가 등록되는지, 브라우저가 이벤트를 주기는
하는지, `deltaMode` 와 `deltaY` 실제 값이 얼마인지를 각각 따로 보게 했다.

남은 것은 두 가지다. 개발 서버가 `no-store` 를 보내게 했고 — 구·신 모듈이
섞이면 오류 없이 조용히 다르게 동작해서 원인을 찾기가 어렵다 —
장치별 휠 값(픽셀·줄·페이지, 휠 마우스·고해상도 휠·트랙패드)을 검증 항목으로
만들었다. 손에 잡히는 장치가 하나뿐인데 심사자가 무엇을 쓸지는 알 수 없다.

### AI에 준 주요 지시

- *"3단계 계획 정리해줘."*
  → 코드가 아니라 계획을 요구했다. 그 결과 투영식을 먼저 풀게 됐고,
  `(x−z, y−z)` 라는 한 줄에서 집기·착시 탐색 공간·깨질 코드 세 곳이 한꺼번에
  나왔다. 바로 구현에 들어갔다면 휠부터 붙이고 지우기가 안 되는 것을
  나중에 만났을 것이다.

- *상한과 기둥 규칙을 선택지로 받아 사람이 골랐다.*
  → 되돌리기 비싼 결정은 사람이 고른다는 상시 지시가 실제로 걸린 자리다.
  특히 기둥 규칙은 표현력과 구조 안정성을 맞바꾸는 결정이라 임의로 고를 수
  없는 종류였다.

- *"휠 안되는거 같아."*
  → 증상만 전달하고 원인을 지정하지 않았다. 코드를 고치는 대신 먼저
  헤드리스로 재현해 로직이 정상임을 확인하고 브라우저 쪽으로 범위를 좁혔다.
  여기서 바로 코드를 만졌다면 멀쩡한 로직을 흔들어 놓았을 것이다.

- *"크롬에서는 잘되는데 파이어폭스에서는 안되네."*
  → 브라우저별 추측을 나열하는 대신 원인을 가르는 진단 페이지를 만들게 했다.
  진단 파일은 저장소에 올라가지 않도록 기존 `SETOUT_*` 제외 규칙을 재사용했다.

- *"검증 스크립트를 저장소에 넣을까?"* 에 대해 넣는 쪽으로 결정.
  → 이 문서가 "검증 스크립트가 설계 판단을 반증했다" 를 근거로 쓰는데
  정작 그 스크립트가 저장소 밖에 있으면 확인할 수 없는 주장이 된다.

## 4단계 — 캐릭터와 이동

### 완성한 것

- 이동 그래프와 최단 경로 (`src/path.js`) — 순수 함수, 6단계 솔버가 그대로 쓴다
- 캐릭터 상태와 이동 (`src/actor.js`)
- 캐릭터·목표 표식 렌더, 깊이 정렬에 캐릭터 끼워 넣기 (`src/render.js`)
- 판 위 좌클릭 = 걷기 (`src/input.js`)
- **밟은 판은 환급하지 않는다** — 2단계에서 남긴 징검다리 구멍을 막았다
- 도착 판정

### 설계 판단

#### 1. 계획서의 중복이 좌표 정리로 풀렸다

계획서에는 "이동 그래프 — 화면상 인접 판정" 이 4단계에, "화면상 한 칸 옆 판정" 이
5단계에 각각 적혀 있었다. 같은 것이 두 번 있는 셈이다.

3단계에서 얻은 `(x, y, z) → 바닥 (x−z, y−z)` 을 쓰면 정리된다.

```
화면상 인접  ⟺  |Δ(x−z)| + |Δ(y−z)| = 1
진짜 인접    ⟺  z 가 같고 |Δx| + |Δy| = 1
```

z 가 같으면 `(x−z, y−z)` 의 차가 그대로 `(x, y)` 의 차이므로
**진짜 인접은 화면 인접의 부분집합이다.** 화면 인접 하나만 구현하면 진짜 길이
공짜로 따라오고, 둘을 가르는 것은 `a.z !== b.z` 한 줄이다.
전수로 확인했다 — 4,320쌍 누락 0.

그래서 5단계에 남는 것은 **가림 처리**뿐이다. 같은 바닥 자리에 판이 겹치면
위의 것만 보이는데, 지금은 보이지 않는 칸도 길로 친다.

#### 2. 보간을 화면 공간에서 한다

계획 단계에서 가장 위험하다고 짚은 지점이고, 실제로 그랬다.

착시 길은 화면상 한 칸 옆이지만 3D 에서는 최대 `Z_MAX` 칸 떨어져 있다.
캐릭터 이동을 격자 좌표에서 보간하면 판을 벗어나 허공을 가로질러 날아간다.
두 끝점을 각각 투영한 뒤 **화면 좌표에서** 보간해야 한다.

이어져 보이니까 건너간 것이므로 이동도 이어져 보이는 그대로여야 한다.
게임의 이름값이 이 한 줄에 걸려 있다.

#### 3. 길찾기를 순수 함수로 묶었다

6단계 디렉터는 **아직 놓지도 않은 배치**에 대고 "이게 풀리는가" 를 물어야 한다.
살아 있는 `board` 를 한 줄이라도 읽으면 그 순간 솔버로 쓸 수 없다.
그래서 `findPath(cells, from, to)` 는 판 칸 스냅샷만 받는다.

도달 여부가 아니라 **경로**를 돌려준다. 솔버의 검증 조건이
"최소 해법이 착시를 요구하는가" 인데, 그것은 경로의 간선을 봐야 답할 수 있다.

화면 자리를 픽셀이 아니라 격자 정수로 계산한 것도 같은 이유다.
카메라·배율과 무관해져야 창 크기와 상관없이 같은 답이 나온다.

#### 4. 밟은 칸 환급률은 0 이어야만 한다

계획서는 "환급을 0 으로 할지 낮출지" 로 열어 뒀는데, 따져 보니 선택지가 아니었다.
`N` 칸 건너기를 두 방식으로 비교하면 (밟은 칸 환급률 `R`)

```
직접 그리기   2N
징검다리      2N − R(N−k)
```

징검다리가 더 싸지 않으려면 `R(N−k) ≤ 0`, 즉 **`R ≤ 0`**.
환급이 조금이라도 남으면 언제나 유리하다.

2단계에서 "환급률로는 막을 수 없다" 는 결론이 나왔던 것과 같은 형태인데,
이번에는 대상이 "밟은 칸" 으로 좁혀졌을 뿐이다. 조건을 밟았는가/아닌가로
갈랐기 때문에 밟지 않은 칸은 여전히 전액 환급을 받는다. 잘못 그린 다리를
걷지 않고 지우면 그대로 돌아오므로 설계 실험은 공짜로 남고, 실제로 지나간
경로만 매몰 비용이 된다. 계획서가 걱정한 "회수 자체를 봉쇄" 는 일어나지 않는다.

#### 5. 캐릭터는 격자 칸만 들고 높이는 판에서 끌어온다

`z` 를 따로 저장하면 캐릭터를 태운 채 판을 휠로 올릴 때 둘이 어긋나
캐릭터만 공중에 남는다. 서 있는 칸의 판에서 끌어오면 갱신할 것이 없다.

덕분에 **판을 태워 올리는 것이 공짜로 따라왔다.** 판을 올려 먼 판과 높이를
맞추는 것이 이 게임의 핵심 조작이므로 막을 이유도 없다.

밟고 선 칸은 지워지지 않게 막았다. 발밑을 빼면 떨어지는 처리를 새로 만들어야
하는데, 서 있는 자리를 못 지우는 것은 설명이 필요 없다.

#### 6. 미결정이던 조작 하나가 저절로 풀렸다

"판에서 눌러 빈 바닥에서 뗐을 때" 를 어떻게 할지가 4단계 시작 전 미결정
사항이었다. 그런데 모드가 `pointerdown` 에서 확정되므로, 판 위에서 눌렀으면
그 순간 이동으로 정해지고 뗀 위치는 볼 이유가 없다.
**누른 칸이 목적지, 뗀 위치는 무시.**

3단계에서 겪은 것도 같은 방향을 가리켰다. 판을 올리면 화면에서 물러나므로
누른 채 커서를 움직이면 판이 커서 밑을 벗어난다. 뗀 지점을 목적지로 잡으면
높은 판일수록 조준이 어긋난다.

#### 7. 기획서의 캐릭터 색을 뒤집었다

기획 단계에서 캐릭터는 흰색 `#EDF2F7` 이었다. 그런데 캐릭터는 언제나 판 위에
선다. 판 윗면이 `#C4CAD2` 라 흰색과 명도가 거의 붙어, 청사진 바닥 위에서였다면
잘 보였을 색이 정작 서 있는 자리에서 묻혔다.

색을 고르는 데 글로 설명하는 것이 무의미해서 **실제 렌더 코드로 후보를 뽑았다.**
캔버스 컨텍스트만 흉내 내고 게임의 `drawFloor` / `drawPlates` / `drawActor` 를
그대로 호출한 뒤, 들어온 그리기 명령을 SVG 로 받아 적는 방식이다.
그림을 따로 그리면 실물과 달라지지만, 이렇게 하면 화면에 나올 도형 그대로다.

고른 것은 코발트 `#2E6FB7` 이다. 격자선 `#39679C` 을 진하게 한 색이라
청사진 팔레트 안에 있으면서 강철판 위에서 떨어져 나온다.
앰버는 후보에서 뺐다 — 목표 표식과 잉크 게이지가 쓰는 색이라
"이것이 자원이다" 라는 뜻이 흐려지고, 무엇보다 화면에서 캐릭터와 목표를
구분할 수 없게 된다.

### 검증 — 2단계 부채 정산

이 단계의 결산이다. 같은 전략을 실제 게임 함수로 그대로 돌려 실측했다.

```
직접 그리기            60칸
징검다리 (환급 있음)   119칸   ← 막기 전
징검다리 (환급 없음)    60칸   ← 지금
```

2단계 기록의 110칸과 숫자가 다른 것은 복도 모양과 선행 확보 칸수가 달라서이고,
결론은 같다. **이제 징검다리로 한 칸도 더 못 간다.**

산수로 확인하면 산수가 맞는지만 알 수 있고 코드가 그 산수대로 도는지는 알 수
없다. 그래서 실제 `beginStroke` / `walkTo` / `beginErase` 를 불러 전략을
시뮬레이션했다.

| 항목 | 결과 |
|---|---|
| 인접 판정 대칭 / 대각 배제 / 자기 자신 배제 | 통과 |
| 진짜 인접 4,320쌍이 전부 화면 인접 | 통과 |
| BFS 최단 거리·도달 불가·우회로 | 통과 |
| 착시로만 이어진 길을 찾는가 / 정직한 길이 있으면 그쪽이 최단인가 | 통과 |
| **`findPath` 가 전역 상태를 안 읽는가** | 통과 |
| 밟지 않은 칸은 절반 환급 그대로 | 통과 |
| 밟은 칸은 한 방울도 안 돌아옴 | 통과 |
| 발밑 칸은 지워지지 않음 / 밟고 선 판을 올리면 같이 올라감 | 통과 |
| 도착 판정 | 통과 |

### 측정이 틀렸다

징검다리를 재려고 16×16 바닥을 뱀처럼 접은 복도를 만들었다.
결과가 70칸으로 나왔다 — 직접 60칸보다 여전히 유리했다.

코드를 의심하기 전에 측정을 봤다. 뱀처럼 빽빽하게 접으면 **위아래 줄이 서로
붙어, 경로상 멀리 떨어진 칸끼리도 사방 인접이 된다.** BFS 는 당연히 복도를
따르지 않고 질러갔고, 질러간 만큼 밟지 않은 칸이 남아 환급을 받았다.
측정하려던 것은 징검다리 전략이지 지름길이 아니다.

짝수 줄만 쓰고 연결 칸을 하나씩만 두어 지름길을 없앴더니 60칸이 나왔다.
그리고 **복도에 지름길이 없다는 것 자체를 검사 항목으로 만들었다.**
이 검사가 없으면 다음에 복도를 손댈 때 같은 자리에 다시 빠지고,
그때는 코드를 의심하게 된다.

3단계가 "읽히지 않는 상태가 구현의 이탈을 드러냈다" 였다면
여기서는 **측정 도구 자체가 틀릴 수 있다**는 쪽이다.
검증이 통과하지 않을 때 코드부터 고치면 멀쩡한 코드를 흔들게 된다.

### AI에 준 주요 지시

- *"4단계 계획 정리해줘."*
  → 3단계와 같은 순서다. 계획을 먼저 요구했더니 계획서 자체의 중복(4·5단계
  이동 그래프)이 드러났고, 미결정 사항 두 개가 계산과 구조로 풀렸다.
  구현부터 했다면 둘 다 취향으로 정하고 넘어갔을 것이다.

- *"캐릭터가 흰색인데 다른색으로 바꿔보고 싶어."*
  → 색은 취향의 영역이지만, 왜 안 보이는지는 취향이 아니다.
  판 윗면과 명도가 붙어 있다는 것을 먼저 짚고 선택지를 대비 기준으로 정리했다.

- *"제안해준 색상 실제 이미지로 보여줘 보고 선택할께."*
  → 글로 색을 고르는 것을 그만두게 한 지시다. 게임의 렌더 함수를 그대로
  호출해 SVG 로 받아 적는 방식을 만들었고, 결과적으로 실물과 다른 그림을
  보고 결정하는 일을 피했다. 판단의 근거를 실물로 옮긴 사례다.

## 5단계 — 착시 연결

### 완성한 것

- 가림 처리 — 보이지 않는 칸은 길이 아니다 (`src/path.js`)
- 캐릭터를 덮는 높이 조절 차단 (`src/board.js`)
- 플레이어 성향 지표 수집 (`src/board.js`, `src/actor.js`) — 6단계 디렉터의 입력
- **세운 판(벽)을 넣지 않기로 확정**

### 착시가 어떻게 생기는가

구현에 앞서 이것부터 정리했다. "벽이 없으면 판을 띄웠을 때 아래 판과 어떻게
연결되는가" 라는 질문이 나왔는데, **아래 판과 연결되는 것이 아니다.**

A 가 바닥에 있고 B 를 `z` 만큼 올렸을 때, `u = xb − xa`, `v = yb − ya` 라 하면
연결 조건은 이렇게 된다.

```
|u − z| + |v − z| = 1
```

정수해는 두 가족뿐이다.

| B 의 위치 | 필요한 높이 | 결과 |
|---|---|---|
| 대각선에서 **한 칸 벗어난** 자리 (`u = v ± 1`) | `z = min(u, v)` | 나란히 선다 → **착시 연결** |
| 대각선 **위** (`u = v`) | `z = u` | 정확히 포개진다 → **가림** |

**대각선은 덮는 축이고, 대각선에서 한 칸 벗어난 자리가 잇는 축이다.**
저 멀리 비스듬히 있던 판을 끌어올려 옆자리에 갖다 놓는 것이 이 게임의
전부이고, 실제로 확인해 보니 A(3,3,z=0) 과 B(8,7) 은 B 를 `z=4` 로 올리면
화면에서 나란히 선다. 3D 에서는 x 로 5칸, y 로 4칸, 높이로 4칸 떨어져 있고
아무것도 닿아 있지 않다.

이 정리가 벽에 대한 판단을 대신했다. 아래 참조.

### 설계 판단

#### 1. 바뀐 것은 사실상 한 줄이다

이동 그래프는 화면 자리마다 그 자리에 오는 칸을 전부 쌓아 두고 모두 이웃으로
내주고 있었다. 그중 **실제로 보이는 것 하나만** 남기면 된다.

무엇이 보이는가는 3단계에서 이미 증명해 뒀다. 같은 자리 `(gx, gy)` 위의
후보는 `(gx+z, gy+z, z)` 뿐이므로

```
depthKey = x + y + z = gx + gy + 3z
```

로 `z` 에 대해 단조증가한다. z 가 가장 큰 것이 언제나 위다.

이것이 태그라인의 역이다. **"이어져 보인다면 이어진 것이다"** 가 성립하려면
보이지 않는 것은 건널 수 없어야 한다. 4단계까지는 판에 파묻힌 칸 위로
캐릭터가 지나갔고, 튜토리얼 문구가 없는 게임에서 플레이어는 무슨 일이
일어났는지 알 방법이 없었다.

#### 2. `pickAt` 을 부르지 않고 같은 규칙을 다시 세웠다

`board.pickAt` 이 이미 "그 자리에서 실제로 보이는 것" 을 돌려준다. 그런데
`path.js` 에서 그것을 부르면 순수성이 깨진다 — `pickAt` 은 살아 있는 `board`
를 읽으므로, 부르는 순간 6단계 디렉터가 아직 놓지도 않은 배치를 물어볼 수
없게 된다.

같은 규칙을 두 곳에 두는 것은 원래 피해야 할 일이지만, 여기서는 **한쪽이
상태를 읽고 다른 쪽이 스냅샷을 읽는다는 차이가 본질적**이다. 대신 둘이
어긋나지 않는지를 검증 항목으로 만들었다(아래 참조).

#### 3. 캐릭터를 덮을 수 없게 했다

가림을 넣고 나서야 보인 문제다. 대각선 위의 판을 그 거리만큼 올리면 화면
자리가 정확히 포개지는데, 그 아래에 캐릭터가 서 있으면 **캐릭터가 화면에서
사라진다.** 자기 말이 어디 있는지 볼 수 없으면 게임이 성립하지 않고,
그 상태를 알려 줄 문구가 이 게임에는 없다.

높이 조절을 시도한 뒤 캐릭터가 보이지 않게 되면 되돌린다.
플레이어에게는 "그 방향으로는 안 올라간다" 로만 보인다.

#### 4. 세운 판(벽)을 넣지 않기로 확정했다

3단계에서 "착시가 실제로 도는 것을 본 뒤 정한다" 로 미뤄 둔 항목이다.

기획서가 벽에 기대한 역할은 "뒤쪽 어긋난 부분을 가려서 이음매를 완성" 이었다.
그런데 **눕힌 판을 올리는 것만으로 잇기와 가리기가 둘 다 나온다.**
대각선 옆은 잇고, 대각선 위는 덮는다 — 위의 정리 그대로다.

게다가 이 게임의 연결 규칙은 "화면상 정확히 한 칸 옆" 이라 어긋남이 애매하게
남는 경우가 없다. 이으면 이어지고 아니면 안 이어진다. 가려서 메울 틈 자체가
없으므로 벽이 할 일이 없다.

반면 넣으려면 더블클릭이나 제스처 같은 발견 불가능한 입력을 만들어야 하고
(튜토리얼 문구 없음 원칙과 충돌), 세운 판의 렌더·깊이 정렬·가림 판정을 새로
짜야 한다. 얻는 것이 없고 드는 것이 크다.

계획 문서의 「보류한 것」에 이유와 함께 남겼다. 못 만든 것이 아니라
따져 보고 안 넣은 것이라는 기록이 남아야 한다.

#### 5. 성향 지표를 쌓기 시작했다

6단계 디렉터는 레벨을 만드는 것이 아니라 플레이어를 읽고 그 사람이 피하는
것을 만든다. 그러려면 성향이 숫자로 남아 있어야 한다.

| 지표 | 읽히는 성향 |
|---|---|
| `inkSpent` | 늘 다리로 밀어붙이는 사람 |
| `illusionSteps` / `realSteps` | 착시만 노리는 사람 |
| `redraws` | 망설이는 사람 |

게임 안에는 아무 표시도 하지 않는다. 알려 주는 순간 "그냥 이어져 보이기만 할 것"
이 아니게 된다.

### 검증 — 세 경로가 같은 것을 보는가

이제 "무엇이 보이는가" 에 세 곳이 각자 답한다.

```
render   깊이 정렬로 나중에 그린 것
board    pickAt 이 z 큰 것부터 훑어 처음 걸린 것
path     화면 자리마다 z 가 가장 큰 것
```

셋이 어긋나면 "이어져 보이는데 못 건너간다" 나 그 반대가 된다.
3단계에서 집기와 렌더를 맞춰 뒀고, 여기서 이동이 합류했다.

| 항목 | 결과 |
|---|---|
| 겹친 자리에서 z 가 큰 것이 보이는가 | 통과 |
| 가려진 칸으로 가는 길이 없는가 | 통과 |
| 잇는 축은 그대로 살아 있는가 (대각선 옆 판을 올리면 6칸 다리) | 통과 |
| **그래프가 보는 것 = `pickAt` 이 보는 것** (배치 40개, 689칸) | 통과 |
| 덮으면 끊기고 내리면 돌아오는가 | 통과 |
| 캐릭터를 덮는 높이 조절이 되돌려지는가 | 통과 |
| 성향 지표가 제대로 쌓이는가 | 통과 |
| `visibleCells` 가 전역 상태를 안 읽는가 | 통과 |

### 검사 시나리오가 또 틀렸다

가림을 넣자 4단계의 「정직한 길이 있으면 그쪽이 최단」이 깨졌다.
확인해 보니 그 배치에서 정직한 다리의 `(1,0,z=0)` 과 곁가지 `(4,3,z=3)` 이
**둘 다 화면 자리 `(1,0)`** 이었다. 가림을 반영하자 z 가 큰 쪽이 이겨 정직한
칸이 가려졌고, 검사가 뒤집힌 것이다.

코드가 아니라 시나리오가 틀렸다. 4단계의 징검다리 복도와 같은 종류다.
그때는 뱀처럼 접은 복도에 지름길이 생겨 있었고, 이번에는 검사 배치에 겹침이
있었다. 둘 다 **측정하려던 것과 다른 것을 재고 있었다.**

배치를 고치면서 "이 배치에 겹치는 화면 자리가 없다" 를 먼저 확인하는 항목을
앞에 넣었다. 겹침을 시험하려는 배치가 아니라면 겹침은 시나리오의 실수이고,
그것을 사람이 눈으로 확인하려 하면 또 놓친다.

검증이 실패했을 때 코드부터 고치면 멀쩡한 코드를 흔들게 된다는 것이
4단계의 교훈이었는데, 같은 일이 한 단계 만에 다시 일어났다.
이제는 실패를 보면 시나리오를 먼저 의심한다.

### AI에 준 주요 지시

- *"벽이 없으면 판을 위로 띄웠을때 아래있는 판이랑 어떤식으로 착시로 연결 할수 있어?"*
  → 이 질문이 5단계의 방향을 정했다. 답하려고 연결 조건을 풀었더니
  `|u − z| + |v − z| = 1` 에서 잇는 축과 덮는 축이 갈라져 나왔고,
  그것이 곧 벽을 넣지 않아도 되는 근거가 됐다. 구현 계획에 없던 정리다.

- *"제안해준 색상 실제 이미지로 보여줘"* 의 방식을 재사용했다.
  → 게임의 렌더 함수를 그대로 호출해 SVG 로 받아 적는 방식으로 착시가 실제로
  성립하는 화면을 뽑아 확인했다. 말로 설명하는 대신 실물을 보고 판단했다.

- *"벽은 넣지 않아도 착시로 충분히 해결할수 있을꺼 같아"*
  → 보류 항목을 사람이 닫았다. 기획서에 있던 코어 메커니즘 하나를 빼는
  결정이라 AI 가 임의로 고를 수 있는 종류가 아니었다.

### 다음

AI 디렉터. 출품의 핵심이고, 여기까지 만든 손잡이가 셋이다 —
잉크 배급량, 환급률, 높이 상한. 읽을 지표도 셋이 쌓이고 있다.
솔버는 `findPath` 를 그대로 쓴다. 같은 코드를 두 번 쓰지 않는 구조가
여기서 값을 한다.

## 6단계 — AI 디렉터

출품의 핵심이다. 커밋 24개로 쌓았고, 검증 묶음이 열에서 열여덟이 됐다.

> AI는 레벨을 만들지 않는다. 플레이어를 읽고, 그 사람이 피하는 것을 만든다.

### 완성한 것

- 층 파라미터 (`src/stage.js`) — 손잡이를 상수에서 층으로 옮겼다
- 최소 잉크 솔버 (`src/solver.js`) — 0-1 BFS. 순수 함수
- 생성 → 검증 → 재설계 루프 (`src/director.js`) — 시드 고정, 실패 이유가 다음 수를 정한다
- 성향 읽기와 맞서는 지시 (`src/profile.js`)
- 층 전환 (`src/session.js`) — 지표만 남기고 나머지를 걷어낸다
- 도면을 넘기는 연출, 발자국, 못 쓰게 된 도면 다시 뜨기
- 렌더 교정 셋 — 이음매의 단, 걷는 중 캐릭터 묻힘, 서 있을 때 묻힘
- 규칙을 색으로 — 미리 깔린 판, 밟은 칸
- 화면 네 모서리 표시 (조작·층 번호·잉크·도면명)

### 설계 판단

#### 1. 솔버는 길찾기가 아니다

이 단계의 뿌리이고 나머지가 전부 여기서 파생됐다.

`findPath` 는 **이미 놓인 판** 위에서 길을 찾는다. 그런데 목표는 빈 바닥 칸이고
플레이어는 판을 **그려서** 간다. 디렉터가 물어야 하는 것은 "길이 있는가" 가
아니라 "배급량 이하의 칸을 그려서 닿는 방법이 있는가" 다.

그래프는 그대로 쓰고 간선에 비용만 붙였다.

```
화면 자리 s 로 한 칸 옮길 때
  s 에 보이는 판 칸이 있다        →  0        (이미 있는 길)
  s 가 비었고 기둥이 안 잡혀 있다  →  INK_COST (그려야 한다)
  기둥이 잡혀 있다                →  통과 불가
```

가중치가 둘뿐이라 우선순위 큐가 필요 없다. 공짜 간선으로 닿는 칸은 같은 층에
계속 얹고 잉크를 먹는 간선만 다음 층으로 넘기면 `path.js` 의 `frontier/next` 와
같은 모양이 된다. 4단계에서 `findPath` 를 순수 함수로 묶어 둔 것이 여기서
회수됐다 — 살아 있는 `board` 를 한 줄이라도 읽었다면 아직 놓지도 않은 배치를
물어볼 수 없었다.

세 번째 갈래가 이 게임의 벽이다. 판을 `z` 만큼 올리면 화면에서는 `(x−z, y−z)`
로 물러나지만 기둥 `(x, y)` 는 계속 잡혀 있어서, 그 자리는 **비어 보이는데 그릴
수도 설 수도 없다.** 5단계에서 벽을 넣지 않기로 확정했는데 지형 도구는 이미
있었다. 코드를 읽다 나온 것이지 설계한 것이 아니다.

#### 2. 판정을 솔버가 아니라 디렉터에 두었다

계획서는 검증 3항목을 `solver.js` 에 두기로 했는데 옮겼다. 판정은 층의 의도와
`candidateCells` 를 알아야 하고, 솔버에 두면 solver → director → solver 로
순환한다. **솔버는 최소 잉크만 재고, 그 숫자로 무엇을 판단할지는 디렉터의 몫으로
남긴다.**

그러자 계획서의 3항목이 전부 두 숫자의 부등식이 됐다.

| 질문 | 판정 |
|---|---|
| 풀리는가 | `illusionCost !== null` |
| 배급량 안에서 풀리는가 | `illusionCost ≤ inkMax` |
| 최소 해법이 착시를 요구하는가 | `honestCost > inkMax` |

세 번째가 중심이다. 착시를 강제한다는 것은 **배급량을 두 값 사이에 끼우는 것**
이고, 그 구간이 비면 어떤 배급량으로도 안 되므로 지형을 다시 설계하라는 신호가
자동으로 나온다.

#### 3. 정직 층의 설계를 실측이 뒤집었다

착시만 노리는 사람에게 낼 층은 "상한을 1 로 조이고 한 칸짜리 판을 올려 벽으로
쓴다" 는 계획이었다. 올린 판은 자기 기둥을 계속 잡으므로 통로가 좁아진다는
계산이다.

200층을 재 보니 **198층에서 착시가 더 쌌다.**

올려 둔 한 칸은 벽이면서 동시에 **공짜 징검다리**다. 딛고 올라섰다 내려오면 한
칸을 안 그리고 넘어간다. 착시만 노리는 사람에게서 도구를 뺏으려던 층이 도구를
나눠 주고 있었다.

상한을 **0** 으로 조여 고쳤다. 판을 올릴 수 없으면 모든 칸이 `z=0` 이고
`isIllusion` 이 참이 될 수 없다. 어렵게 만든 것이 아니라 **구조적으로 불가능하게
만든 것**이라 200층 전부 두 값이 같다. 1단계에서 `BLOCK_H = TILE_H` 를 참조로
둔 것과 같은 방식이다.

구조물은 바닥에 눕혀 벽이 아니라 공짜 지름길로 쓴다. 배급이 조인 층에서는 그
지름길을 찾아 꿰는 것이 그대로 퍼즐이 된다.

#### 4. 배급을 0 에서 출발시킨다

재설계 루프의 모양을 정하는 결정이다. 얼마를 줘야 하는지 미리 정해 두지 않고
**첫 판정이 반드시 실패하게** 만든 다음, 그 실패가 짚어 주는 최소값을 받는다.
지형이 바뀌면 배급이 저절로 따라오고, 배급표를 손으로 관리할 일이 없다.

실패는 이유만 대지 않고 방향을 준다. **무작위로 다시 뽑기만 하면 절차적 생성이지
에이전트가 아니다.** 배급 문제면 같은 지형에 배급만 바꿔 다시 묻고, 지형 문제면
새로 뽑는다.

루프가 생성기의 결함을 두 번 드러냈다.

**하나.** 200번 돌려 재 보니 층의 절반이 배급 10(5칸) 이하였다. 시작점을 이음매
바로 옆(1~3칸)에 놓은 탓이다. 이음매가 공짜로 실어 주는 것이 요점이니 가까울수록
좋다고 봤는데, 판 하나 긋고 끝나는 것은 층이 아니다. 5~9칸으로 떨어뜨리고
`MIN_CELLS` 를 6 에서 10 으로 올렸다.

**둘.** 그러자 재설계율이 62% 로 뛰었다. 착시 층에서 그리기 값은 사실상 시작에서
목표까지의 맨해튼 거리다 — 공짜로 밟을 수 있는 것은 올려 둔 이음매뿐인데 거기에는
정직하게 발을 디딜 수 없기 때문이다. **생성기가 그 자리에서 알 수 있는 것을 솔버에게
묻고 있었다.** 미리 거르게 하니 62% 가 1% 로 떨어졌고 평균 시도가 4.1 에서 3.0 이
됐다. 400개 시드 전부 성공한다.

#### 5. 깊이의 척도가 틀렸다

`TOO_SHALLOW` 를 의도한 해법의 길이로 쟀더니 **100층 중 97층이 걸렸다.**

착시 층은 설계상 그리는 칸이 적다. 이음매가 공짜로 실어 주는 것이 요점이라 서너
칸만 그으면 닿는다. 잘 만든 착시 층을 전부 떨어뜨리고 있었다.

**층이 시시한 것은 그리는 칸이 적어서가 아니라 그냥 그려서 가도 싸서다.** 척도를
`honestCost` 로 바꾸니 97 에서 21 로 떨어졌고, 남은 21층은 실제로 목표가 가까운
얕은 층이다.

#### 6. 디렉터가 자기가 낸 층을 다시 읽고 있었다

**이 단계에서 가장 중요한 발견이다.** 맞서는 층만 내면 4층째부터 성향이 무엇이든
같은 순서가 나왔다.

착시를 강제하면 누구나 이음매를 건너고, 정렬을 없애면 아무도 못 건넌다. 그러면
디렉터가 만든 층이 다음 판단의 입력이 된다. **읽었다고 한 것이 사실은 자기가
직전에 낸 층이었다.** 플레이어를 읽는다는 말이 성립하지 않는다.

세 번째 의도를 넣었다 — 둘 다 갈 수 있는데 착시가 싼 층이다. 새 지형은 필요
없고 같은 이음매 층에 배급을 그리기 값 위로 주면 된다. 지금까지 `ILLUSION_UNUSED`
로 떨어뜨리던 바로 그 상황을 일부러 내는 것이고, **여기서 싼 길을 골랐는지 비싼
길을 골랐는지가 디렉터가 만들지 않은 유일한 정보다.**

판정은 셋을 요구한다. 둘 다 배급 안에 들 것, 착시가 더 쌀 것, 그 차이가 3칸 이상일
것. 마지막이 없으면 어느 쪽을 골라도 비슷해서 그 선택은 성향이 아니라 그날의
기분이다.

부수 효과로 히스테리시스가 필요 없어졌다. 문턱 사이를 "하던 것 유지" 로 두려던
것이 바로 자기가 낸 층을 다시 읽는 증상의 대증요법이었다. **이제 애매하면
물어본다.**

선택 말고는 아무것도 다르지 않은 두 사람을 10층씩 돌려 확인했다. 전에는 4층째부터
같아졌는데 이제 정반대 층을 받는다.

```
착시를 고르는 사람 : 물어봄 정직강제 물어봄 정직강제 정직강제 물어봄 …
그려서 가는 사람   : 물어봄 착시강제 정직강제 물어봄 물어봄 물어봄 …
```

#### 7. 배급에 헛디딜 여유를 얹는다

배급을 최소 해법에 정확히 맞추면 플레이어는 한 칸도 헛디딜 수 없다. 헛디딘 다리를
**걸어 본 순간** 그 잉크는 영영 안 돌아오기 때문이다 — 2·4단계에서 징검다리를
막으려고 밟은 칸 환급을 0 으로 정했던 것이 여기서 되돌아왔다.

1층에서는 배급이 120(60칸)이라 드러나지 않았다. 디렉터 층은 16~30 이라 실측하니
실제 여유가 **중앙값 2칸, 최소 0칸**이었다. 2칸을 얹으니 200층 중 182층이 살아남고
나머지는 루프가 다시 뽑는다. 착시를 강제하는 성질은 그대로다 — 여유를 얹고도
그리기 값보다 낮으면 되기 때문이다.

#### 8. 복잡도는 성향이 아니라 시트 번호가 쥔다

구조물을 얼마나 얹을 것인가를 아무도 쥐고 있지 않아서 그 값이 의도에 딸려 왔다.

```
illusion / open   구조물 1개 / 5~7칸
honest            구조물 6~7개 / 23~30칸
```

착시파로 읽히면 두 장째부터 여섯 개짜리 빽빽한 판을 받고, 다리파로 읽히면 여섯
장째까지 구조물이 하나뿐이었다. **익히는 판은 누가 플레이하든 익히는 판이어야
한다.** 성향이 정하는 것은 무엇을 묻는 층인가이지 얼마나 빽빽한가가 아니다.

시트 1~2 가 익히는 판, 3부터 다 자란 판이다. 사이 단계는 두지 않았다 — 완만하게
올리면 다 자란 판이 다섯 장째에나 온다.

#### 9. 구조물을 자기 회피 보행으로

구조물이 한 축으로만 더한 직선이라 열 층을 내면 열 층이 다 같은 모양이었다.
한 칸씩 걷는 것으로 바꿨더니 직선은 그중 한 결과로 남고 ㄱ·ㄷ·계단·S 가 같이
나온다(곧은 34% / 꺾인 66%). 곧게 가던 방향에 가중치 3 을 실었다 — 네 방향을
고르게 뽑으면 구불구불한 것만 나오는데, **직선이 안 나오는 것도 다양한 것이 아니다.**

한 줄로 이어져 있다는 것은 모양 문제만이 아니라 셋을 한꺼번에 지킨다.

| 성질 | 그래서 |
|---|---|
| 같은 `z` 위의 4방향 인접이라 전부 진짜 길 | 걸어서 건너는 이음매가 된다 |
| `z` 가 하나뿐이라 화면 자리가 일대일 | 자기끼리 안 겹친다 |
| 양 끝이 남는다 | 끝에 목표를 붙이는 규칙이 그대로 산다 |

이음매에는 **끝점 거리** 조건을 걸었다. 이음매의 값은 칸 수가 아니라 두 끝 사이의
거리다 — 접혀서 제자리로 돌아오는 보행은 여덟 칸을 써도 두 칸짜리 이음매이고,
그러면 그리기 값이 안 커져 배급을 끼울 자리가 없어진다. 실측하니 시도 100번 중
36번이 `NO_BUDGET_WINDOW` 였고 걸린 것이 전부 이 부류였다.

### 화면이 규칙을 배신하고 있었다

디렉터가 이음매를 미리 올려 두기 시작하자, 5단계까지 한 번도 안 나타나던 렌더
문제가 셋 드러났다. **이동 규칙은 한 줄도 안 바꿨다** — 규칙이 틀린 것이 아니라
화면이 규칙을 배신하고 있었다.

**하나 — 이음매에 단이 진다.** 판은 바닥 마름모를 두께만큼 올려 그리므로 윗면이
뒤쪽 칸의 마름모 안으로 파고들고, 뒤칸의 옆면이 있어야 할 자리가 바로 거기다.
앞칸 윗면이 뒤칸 옆면을 덮어 주면 맞물리고, 못 덮으면 두께가 단으로 남는다.
누가 나중에 그려지는가는 `depthKey = (화면 gx + gy) + 3z` 가 정하는데, 앞칸은
`gx+gy` 가 1 클 뿐이라 **뒤칸이 한 칸이라도 높으면 `3z` 가 그 1 을 덮어쓴다.**
그래서 같은 착시가 방향에 따라 달라 보였다 — 왼아래·오른아래는 매끈하고
왼위·오른위는 단이 졌다. 옆면과 윗면을 두 벌로 나눠 고쳤다. 고치기 전 렌더로
되돌리면 단이 진 쌍 14개가 뒤칸이 더 높은 쌍 14개와 정확히 일치한다.

**둘 — 건너는 동안 캐릭터가 묻힌다.** 깊이 정렬에 캐릭터를 **떠나는 칸**에 얹고
있었다. 도착할 칸은 카메라 쪽으로 걸을 때 정렬 키가 더 커서 캐릭터보다 나중에
그려지고, 그 윗면이 캐릭터를 덮는다. 진짜 길은 키 차이가 1 이라 발치가 조금
잘리는 정도인데 **착시 길은 `3z` 만큼 벌어져 판 속으로 들어간다.** 실측한 자리는
`(6,9,z=0) → (11,13,z=5)`, 키 15 → 29, 캐릭터 픽셀이 167 에서 20 으로 떨어졌다.

**셋 — 서 있기만 해도 묻힌다.** 이음매 6칸을 올려 두고 바닥 250칸을 전수로 재면
13칸에서 가려지고 그중 6칸은 머리까지 묻혔다. 최악이 80% 였다. 캐릭터를 판 전부
다음에 그려 고쳤다. 원래 주석은 "맨 뒤에 그리면 앞칸 판을 뚫고 보인다" 였는데
확인해 보니 그렇지 않았다 — 캐릭터 실루엣은 자기 칸 한가운데에서 위로 솟은 좁은
기둥이라 겹칠 수 있는 것은 화면상 위쪽 칸뿐이고, 그것들은 캐릭터보다 뒤에 있는
판이다. **주석이 사실이 아닌 것을 확인하지 않고 믿고 있었다.**

셋 다 "자기 말이 어디 있는지 못 보면 게임이 성립하지 않는다" 는 같은 규칙에
걸린다. 5단계에서 "캐릭터를 덮는 높이 조절을 되돌린다" 로 한 번 막았는데, 그때는
**판을 올릴 때만** 봤다.

### 규칙은 화면에서 읽혀야 한다

5단계에서 "게임 안에 아무 표시도 하지 않는다" 로 정한 것은 **성향 지표**이지
규칙이 아니다. 이 단계에서 규칙을 화면으로 옮긴 자리가 셋이다.

| 무엇 | 안 하면 어떻게 읽히는가 |
|---|---|
| 미리 깔린 판을 청사진 쪽 색으로 | 지우개를 문질러도 아무 일이 없다 = 고장 |
| 밟은 칸을 빛이 죽은 철판으로 | 나중에 지웠는데 게이지가 안 찬다 = 고장 |
| 되받을 수 있는 잉크를 게이지 한 겹으로 | 걸어 본 순간 화면에서 아무 일도 안 일어난다 |
| 발자국 — 올린 판이 남긴 구멍을 점선으로 | 잉크는 남았는데 선만 안 나온다 |

발자국은 3단계부터 있던 구멍인데 그때는 올리는 것이 플레이어 자신이라 "내가
저기서 올렸지" 로 넘어갔다. **디렉터가 이음매를 미리 올려 두면서 처음 드러났다** —
층당 다섯 칸꼴이었다. 점선으로 그렸다. 아직 그리지 않은 것은 선이고, 발자국은
그린 것이 아니다.

색은 넷 다 실제 렌더 함수를 불러 후보를 뽑아 놓고 골랐다. 4단계에서 캐릭터 색을
고를 때 만든 방식 그대로다. 앰버와 코발트는 후보에서 뺐다 — 앰버는 자원의 색이고
코발트는 내 말의 색이라 지형에 쓰면 뜻이 흐려진다.

### 판정이 보증한 층과 실제로 푸는 층이 달랐다

미리 깔린 판이 **우클릭으로 지워졌고 환급까지 나왔다.** 구조물 6칸에서 잉크
16 → 22 였다.

`erase` 의 `Math.min(inkMax, ...)` 로 막았다고 적어 두었는데 그건 배급을 넘지
못하게 할 뿐이다. 한 번이라도 잉크를 쓰고 나면 상한에 안 걸리므로 구조물을 지우는
것이 언제나 벌이가 된다. 잉크만의 문제도 아니다 — **솔버가 "이 층은 배급 안에서
풀린다" 를 보증한 근거가 이 지형인데, 그것을 공짜로 걷어내면 판정이 보증한 층과
실제로 푸는 층이 달라진다.**

그 위에서 막힘 판정이 조용히 죽어 있었다. 되받을 수 있는 잉크를 "밟지 않은 칸
전부" 로 세었는데 구조물이 거기 들어갔다. 남은 잉크 16 / 필요 18 / 세어 준 환급 6
이라 "안 막힘" 이 나왔지만 **그 6 은 지울 수가 없었다.** 구조물 6칸을 지우는
64가지를 전부 돌려 봐도 풀리는 경우가 없었고, 화면은 4초를 기다려도 그대로 멈춰
있었다 — 이 기능이 없애려던 상태가 정확히 그것이다.

막힘 판정 자체는 가장 너그러운 쪽으로 잡았다. **잉크가 떨어진 것과 막힌 것은
다르다.** 목표로 다리를 긋다 바닥나는 것은 지우고 다시 그으면 되는 상태이고, 그
사이에 도면을 걷어 가면 플레이어는 무엇을 잘못했는지도 모른 채 판을 뺏긴다.
필요한 잉크는 하한을, 가진 잉크는 되받을 수 있는 환급을 전부 더한 상한을 쓴다.
하한이 상한을 넘으면 어떤 순서로 무엇을 지워도 안 된다.

막혔을 때는 **같은 층을 다시 뜬다.** 새 층을 내지 않는다 — 플레이어가 풀려던
문제가 이것이고, 실패했다고 다른 문제를 내밀면 방금까지 읽던 것이 무의미해진다.

### 층이 넘어가는 한복판이 위험하다

층 전환은 **지표만 남기고 나머지를 전부 걷어내는 일**이다. `stats` 를 지우면
디렉터가 매 층 백지에서 읽게 되고, 그러면 플레이어를 읽는다는 말이 성립하지
않는다. 나머지는 전부 그 층의 것이라 지운다.

계획서가 미리 짚어 둔 `fitView` 함정은 구조적으로 없앴다. 층마다 상한이 다른데
(정직 층 0, 착시 층 8) 다시 안 잡으면 이전 층의 여유로 그려 판 머리가 잘리고,
잘린 것은 화면 밖이라 잘렸다는 것조차 보이지 않는다. 부르는 쪽이 창 크기를 들고
있어야 하는 것이 문제였으므로 `iso` 가 마지막 크기를 기억하게 하고 `refit()` 한
줄로 줄였다.

그리고 **넘기기 직전에 이미 시작된 제스처**가 남아 있었다. 도착하고 0.8초 뒤에
넘어가므로 손이 아직 붙어 있는 것은 드문 일이 아닌데, 이전 층에 대고 긋던 획이
새 층에 확정됐다. 실측하니 새 층 배급 22 중 8을 먹었고 지우개 쪽은 새 층의 고정
구조물을 지웠다. **배급이 조여진 층에서 3분의 1이 다른 층에서 시작한 드래그로
날아간다.** 넘기기 직전에 하던 제스처를 놓는다 — 어느 층에 그은 것인지가 정해지지
않은 획이라 확정할 근거가 없다.

### 판단 기록 — 실물

계획서가 "각 시도의 `{시도번호, 실패코드, 한 줄 이유, 다음 수정}` 을 배열로
남긴다" 고 못 박은 것이다. 콘솔과 이 문서에만 남기고 화면에는 띄우지 않는다 —
띄우면 플레이어가 자기가 읽히고 있다는 것을 알아 행동이 바뀌고, 그러면 읽은
성향이 성향이 아니게 된다.

배급을 0 에서 출발시키므로 **첫 시도는 언제나 실패한다.** 그 실패가 최소값을
짚어 주는 것이 설계다.

아래는 `formatLog` 출력 그대로다. 성향 지표만 반대로 넣은 두 사람이다.

**다리로 미는 사람 — 2층째**

```
디렉터 — 시드 7, 3번 시도, 냈다
  읽음: 1층째 — 층당 착시를 0.0번밖에 안 건넜다. 그리기만으로는 못 가는 층을 낸다. 배급의 98% 를 쓰고 망설임이 11% 다. 여유를 줄인다. 아직 익히는 판이라 구조물은 적게 둔다.
  1. [OVER_BUDGET] 최소 해법 18 에 여유 4 을 얹으면 배급 0 를 넘는다. 딱 맞추면 한 칸도 헛디딜 수 없다.  (착시 18 / 그리기 24, 배급 0)
       → 배급을 22 로 올린다.
  2. [OK] 착시로 18, 그리기만으로는 24. 배급 22 안에서는 착시뿐이다.  (착시 18 / 그리기 24, 배급 22)
  3. [OK] 착시로 18, 그리기만으로는 24. 배급 22 안에서는 착시뿐이다.  (착시 18 / 그리기 24, 배급 22)
       → 창 22~22 에서 22 을 골랐다.
  낸 층: 배급 22, 상한 8, 시작 (13,13) → 목표 (10,4)
       2번 꺾인 판 6칸을 z=2 로 올려 목표 옆에 세웠다. 3D 에서는 2칸 떨어져 있고 아무것도 닿아 있지 않다. 곁에 뜬판 2개를 더 놓아 고를 것을 만들었다.
```

**착시만 노리는 사람 — 4층째**

```
디렉터 — 시드 11, 3번 시도, 냈다
  읽음: 3층째 — 층당 착시를 2.0번 건넜다. 맞출 정렬이 없는 층을 낸다. 배급의 80% 를 쓰고 망설임이 28% 다. 여유를 줄인다.
  1. [OVER_BUDGET] 정직한 최소 해법 28 에 여유 4 을 얹으면 배급 0 를 넘는다.  (착시 28 / 그리기 28, 배급 0)
       → 배급을 32 로 올린다.
  2. [OK] 그리기만으로 28 에 풀린다. 맞출 정렬은 없다.  (착시 28 / 그리기 28, 배급 32)
  3. [OK] 그리기만으로 28 에 풀린다. 맞출 정렬은 없다.  (착시 28 / 그리기 28, 배급 34)
       → 창 32~42 에서 34 을 골랐다.
  낸 층: 배급 34, 상한 0, 시작 (14,15) → 목표 (1,10)
       높이 상한을 0 으로 조였다. 올릴 수 있는 판이 없으니 맞출 정렬도 없다. 바닥에 18칸을 미리 깔고, 뜬판 2개 3칸을 z=3·4 로 띄웠다 — 경로에서 1칸 더 비켜 있어 딛고 돌아도 한 칸을 못 아낀다.
```

앞사람에게는 착시를 강제하는 층(상한 8, 이음매)이, 뒷사람에게는 정렬을 없앤 층
(상한 0)이 갔다. 지표 말고 다른 입력은 없다.

재설계 루프가 실제로 도는 것은 요구를 조여야 볼 수 있다. 기본 배치는 4번 판단에서
미리 거르므로 대개 한 번에 통과한다. 아래는 `minCells` 를 14 로 올린 시드 9 다.

```
디렉터 — 시드 9, 6번 시도, 냈다
  1. [TOO_SHALLOW] 그냥 그려도 10칸이면 닿는다. 층이라고 할 것이 없다.  (착시 14 / 그리기 20, 배급 0)
       → 목표를 밀어낸다 — 그리기로 최소 14칸.
  2. [TOO_SHALLOW] 그냥 그려도 11칸이면 닿는다. 층이라고 할 것이 없다.  (착시 12 / 그리기 22, 배급 0)
       → 목표를 밀어낸다 — 그리기로 최소 14칸.
  3. [TOO_SHALLOW] 그리기로는 못 가지만 착시로 7칸이면 닿는다. 층이라고 할 것이 없다.  (착시 14 / 그리기 —, 배급 0)
       → 목표를 밀어낸다 — 그리기로 최소 14칸.
  4. [OVER_BUDGET] 최소 해법 8 에 여유 4 을 얹으면 배급 0 를 넘는다. 딱 맞추면 한 칸도 헛디딜 수 없다.  (착시 8 / 그리기 30, 배급 0)
       → 배급을 12 로 올린다.
  5. [OK] 착시로 8, 그리기만으로는 30. 배급 12 안에서는 착시뿐이다.  (착시 8 / 그리기 30, 배급 12)
  6. [OK] 착시로 8, 그리기만으로는 30. 배급 20 안에서는 착시뿐이다.  (착시 8 / 그리기 30, 배급 20)
       → 창 12~28 에서 20 을 골랐다.
  낸 층: 배급 20, 상한 8, 시작 (11,4) → 목표 (2,2)
       곧은 판 5칸을 z=8 로 올려 목표 옆에 세웠다. 3D 에서는 8칸 떨어져 있고 아무것도 닿아 있지 않다. 곁에 뜬판 8개를 더 놓아 고를 것을 만들었다.
```

3번 시도의 `그리기 —` 는 그리기만으로는 아예 못 가는 지형이라는 뜻이다. 그럴 때
깊이는 착시 값으로 대신 재고(`honest ? honest.cost : illusion.cost`), 문구도 그렇게
말한다.

**이 문구는 이 기록을 쓰면서 고쳤다.** 원래는 어느 갈래든 "그냥 그려도 7칸이면
닿는다" 였는데, 그리기로 못 가는 층에 그렇게 적히면 바로 옆의 `그리기 —` 와
어긋난다. 판정은 맞고 설명만 뒤처진 것이라 화면에는 증상이 없다. 증상이 없는데도
고친 이유는 **이 기록이 제출물 4번의 증거이기 때문**이다 — 값과 문구를 나란히
찍어 놓고 둘이 어긋나면 읽는 사람은 판정을 의심하게 된다.

로그를 요약하지 않고 실물로 실으면 이런 것이 걸린다. 3단계에서 검증 스크립트를
저장소로 옮긴 것과 같은 이유이고, 결과도 같았다.

지형 문제로 세 번 새로 뽑은 뒤 배급 문제로 한 번 고치고 통과했다. **실패 코드가
다음 수를 갈랐다** — 앞의 셋은 새 지형을 뽑았고 넷째는 같은 지형에 배급만 바꿨다.

난수는 시드를 고정했다. `Math.random` 을 쓰면 "400개 시드 전부 통과했다" 가
확인할 수 없는 주장이 되고, 디렉터가 왜 그 층을 냈는지도 그때 그랬다로만 남는다.
3단계에서 검증 스크립트를 저장소로 옮긴 것과 같은 이유다.

| `solver` | 낸 잉크 22 를 **실제로 그어** 정확히 22 를 쓰고 클리어 / 정직하게는 34 |
| | 올린 판이 남긴 구멍이 솔버에서도 통과 불가 — 4(2칸)로 갈 길이 8(4칸)이 된다 |
| | 기둥을 `cells` 에서 유도한 결과가 `board.occupied` 와 일치 |
| `director` | 착시 층·정직 층을 각각 100개 시드에서 전부 낸다 (100/100) |
| | 짚어 준 대로 고치면 그 실패가 다시 안 난다 — 100층에서 0건 제자리 |
| | 통과한 층은 최소 해법이 **실제로 착시 간선을 쓰는지** 경로로 되짚음 |
| | 구조물 200층이 전부 `zTop` 안 / 카메라 여유가 가장 높은 것을 덮는다 |
| `profile` | 성향을 넣으면 반대 방향 층이 나온다 / 같은 시드 → 같은 층 |
| | 지표를 변형하지 않는다 / 층을 내도 `board` 는 그대로다 |
| `stage` | 손잡이를 돌리면 게임이 따라온다 (옮겼는데 안 읽히면 증상이 없다) |
| `session` | 기둥과 판이 매 층 정확히 맞는다 (유령 0 / 누락 0) / 지표는 층을 넘어 누적된다 |
| `seam` | 실제 `drawPlates` 를 불러 칠해진 순서대로 이음매 색을 하나씩 본다 |
| `footprint` | 층 60개에 사각지대 409칸 — 전부 표시된다 |
| `hud` | 안내에 적힌 라벨을 꺼내 실제 `attachPointer` 에 이벤트를 쏴서 대조 |

`seam` 은 픽셀을 만들지 않고 화가 알고리즘만 흉내 낸다. 외부 라이브러리를 하나도
안 쓰는 게임이 검증에만 의존성을 들이면 "설치 없이 실행" 이라는 전제가 흐려진다.

**고치기 전으로 되돌려 실패하는 것을 확인한 검사**가 셋이다. 이음매의 단(14쌍),
걷는 중 묻힘(착시 4·7 프레임, 진짜 길 10·10 프레임), 서 있을 때 묻힘(250칸 중
13칸). 통과하는 검사는 통과할 뿐이고, 그 검사가 실제로 무엇을 잡는지는 깨뜨려
봐야 안다.

### 실패를 보면 시나리오를 먼저 의심한다

4·5단계에서 두 번 다 코드가 아니라 시나리오가 틀렸으므로, 이 단계에서는 **"이
배치에 겹치는 화면 자리가 없다" 를 검사 앞에 먼저 넣는 것**을 규칙으로 삼았다.
그리고 실제로 두 번 더 걸렸다.

**하나.** 검증 3항목을 쓰면서 배급 0 이면 무조건 `OVER_BUDGET` 이 난다고 보고,
`TOO_SHALLOW` 라는 정당한 재설계 신호를 "제자리" 로 세고 있었다. 판정이 아니라
검사가 틀렸다.

**둘.** 색이 갈린 두 판의 이음매 검사를 쓰다 배치를 틀렸다 — 구조물의 화면 자리가
내 판을 덮고 있었다. 전제 검사를 앞에 넣어 두었더니 그 자리에서 걸렸다.

3단계가 "읽히지 않는 상태가 구현의 이탈을 드러냈다", 4단계가 "측정 도구 자체가
틀릴 수 있다", 5단계가 "검사 시나리오가 또 틀렸다" 였다면, 여기서는 그것을 **검사
항목으로 만들어 두면 다음에 안 걸린다** 는 쪽이다. 사람이 눈으로 확인하려 하면
또 놓친다.

### AI에 준 주요 지시

- *"6단계 계획 정리해줘."*
  → 3·4단계와 같은 순서다. 계획을 먼저 요구했더니 "솔버는 길찾기가 아니다" 가
  나왔고, 거기서 0-1 BFS·검증 3항목·실패 코드·재설계 루프가 한꺼번에 파생됐다.
  코드부터 시작했다면 `findPath` 를 그대로 불러 놓고 "왜 답이 이상하지" 를
  한참 뒤에 만났을 것이다.

- *"판정을 solver 에 두는 게 맞아?"* 에 대해 director 로 옮기는 쪽으로 결정.
  → 계획서를 고친 자리다. 순환 의존이 생기는 것을 근거로 사람이 골랐다.

- *"착시만 노리는 사람한테 낼 층은 상한을 1 로 조이면 되지 않나?"*
  → 그대로 구현하지 않고 200층을 실측하게 했더니 198층에서 착시가 더 쌌다.
  2단계의 "판을 그릴 수 있는 개수가 너무 적다" 와 같은 종류다 — 요청을 그대로
  실행하지 않고 목적을 되짚었다.

- *"디렉터가 성향을 제대로 읽는지 가상 플레이어로 돌려 봐."*
  → 이 지시가 6번 판단을 통째로 끌어냈다. 검사를 요구한 것인데 나온 것은
  설계 결함이었다 — 읽었다고 한 것이 자기가 낸 층이었다. 2단계에서 검증이
  설계 판단을 반증한 것과 같은 자리다.

- *"이음매 넘어갈 때 캐릭터가 판에 묻히는 것 같아."*
  → 증상만 전달했다. 원인이 깊이 정렬의 어느 칸에 얹느냐였고, 고치기 전
  정렬로 되돌려 실패하는 것까지 확인한 검사가 여기서 나왔다.

- *"색상 실제 렌더로 뽑아서 보여줘."*
  → 4단계에서 만든 방식을 이 단계에서 네 번 재사용했다(미리 깔린 판, 밟은 칸,
  게이지 겹, 발자국). 글로 색을 고르는 일이 한 번도 없었다.

- *"커밋 네 개로 나눠줘."*
  → 성격이 갈리는 변경을 한 덩어리로 올리지 않는다. 나누면서 커밋마다 그 시점
  트리를 뽑아 `node test/run.mjs` 를 돌려, **어느 커밋으로 되돌려도 도는 것**을
  확인했다. 2단계에서 커밋 넷으로 나눌 때 세운 규율 그대로다.

## 설계의 뿌리 — 잉크 경제

이 게임의 나머지 규칙이 전부 여기서 파생되므로 따로 적어 둔다.
구현 이전, 기획 단계의 판단이다.

**문제.** 그리기와 착시가 같은 문제를 푸는 경쟁 관계였다.
다리를 그려서 건널 수 있는데 굳이 어려운 착시를 쓸 이유가 없다.
게임의 정체성인 착시가 아무도 쓰지 않는 장식 기능이 된다.

**원인.** 착시로 길을 잇는 퍼즐은 보통 플레이어가 아무것도 만들 수 없기 때문에
착시가 유일한 해법이 된다. 그런데 이 게임은 창조 능력을 준다.
주는 순간 착시의 존재 이유를 없애 버린 것이다.

**선택지.** 그리기를 빼면 기존 장르의 반복이 되고,
착시를 빼면 이 장르에 들어온 이유가 사라진다.
남은 길은 둘을 화해시키는 것뿐이었다.

**해법.** 그리는 데 잉크가 들고, 잉크는 유한하며, 착시는 공짜다.

**결과.** 다리는 여전히 그릴 수 있지만 비싸진다.
잉크가 조일수록 착시를 쓸 수밖에 없어지고, 착시는 선택이 아니라 실력이 된다.
같은 스테이지를 초보는 다리로, 숙련자는 눈속임으로 푼다.

**부수 효과.** AI 디렉터가 쥘 손잡이가 생겼다.
잉크 배급량 숫자 하나로 난이도와 플레이 성향을 동시에 조절할 수 있고,
솔버의 검증 조건도 "배급량 안에서 풀리는가",
"최소 해법이 착시를 요구하는가"로 명확해진다.

**일반화.** 두 기능이 충돌하면 하나를 버리기 전에
한쪽을 비싸게 만들 수 있는지 본다.
무한한 자원은 최적해 하나로 수렴하지만,
유한한 자원은 매번 다른 판단을 요구한다.
